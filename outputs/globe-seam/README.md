# 球面上的接缝：从哪来、怎么定位、修成什么样

用户指出"一些星球有很明显的接缝，这在 main 中是没有的"。查下来是**球面网格的接缝列被重新计算的法线劈开了**：
`body-geometry.js` 给有了 `shape` 的天体克隆球体、按半轴缩放位置，然后用 `computeVertexNormals()` 重算法线。
球体的 UV 接缝是一列**重复顶点**（同一位置，u=0 与 u=1），逐面平均只看得见各自一侧的面，
于是两列法线不同——着色沿整条子午线折一道；极点处三角扇退化，法线干脆算不出来（长度为零）。
main 里这颗星球多数没有 `shape`，用的是 three.js 自己那份解析法线，所以看不到；本分支给 53 个天体
（包括所有行星）补上实测半轴，接缝就跟着上屏了。

修法是把"重算"换成"变换"：球体被线性映射成椭球，法线就是该映射的逆转置作用在原法线上；
带赤道脊时多一个随纬度变化的赤道缩放，其雅可比的逆转置有闭式解。
两种写法都不依赖面的邻接关系，重复列自然算出同一个法线，极点也正常。

## 量到的

同一个球（112×80 段）在两种法线下的差异：

| 量 | `computeVertexNormals` | 解析变换 |
| --- | --- | --- |
| 接缝重复列的法线夹角 | 3.30° | 0.00002°（浮点噪声） |
| 极点法线 | 长度为零（退化） | 正常单位向量 |
| 与椭球真实法线的最大夹角 | 90°（极点处） | 0.015°（与有限差分参考之差，即差分本身的误差） |
| 偏离超过 1° 的顶点 | 318 / 9153（其中 226 个在极点） | 0 |

着色台阶的上界就是法线夹角乘表面亮度：3.3° 在中等受光处约合 3–5/255 —— 单看不显眼，
但沿整条子午线连贯成一条直线，眼睛很容易捕捉，这就是用户圈出来的那条缝。

## 怎么复现

```bash
npm run dev
# 相机绕身体一周，每个取景拍一张；同一命令用改动前/后的代码各跑一次
ATLAS_URL=http://127.0.0.1:5173 TAG=fixed BODY=uranus VIEWS=12 node scan-seam-views.mjs
```

把两次的输出逐像素相减，差异会集中在少数几列上（改动前后一次实测：view 0 在 x=485–488、
view 1 在 437–439、view 8 在 72–74、view 9 在 87–89 各成一条**窄列簇**，即那条子午线；
view 3、5、11 为 0，因为那些取景里接缝落在背光面）。`meridian-step.mjs` 按天体姿态算出接缝子午线的
屏幕位置并沿它量台阶，`shoot-with-state.mjs` 是配套的截图脚本。

**回归守卫在单元测试里**：`solar-system/tests/body-models.test.js` 的
「a shaped globe keeps one normal per surface point, seam and poles included」断言
接缝两列夹角 < 0.05°、法线全是单位长度、且与参数曲面的有限差分法线相差 < 0.05°，
并带一条反向对照（旧的逐面平均必须仍然超过 0.5°，否则测试本身失效）。
对着未修的 `body-geometry.js` 跑，它以「2 normals are not unit length」失败。

像素级阈值没有做成长期断言：这条缝只有 3–5/255 的幅度，与云带自身的横向梯度同量级，
可靠的判据是几何量而不是像素差。这一点写在这里而不是含糊过去。
