# 环与行星的亮度尺度：量测与订正

问题：环的着色器把自己的反射率（I/F）直接写进片元颜色，而行星走 three 的标准路径
（`albedo/π × 光强 × N·L`）。两者是不是在同一个亮度尺度上，差多少？

```bash
npm run dev
TAG=default2026 node shoot.mjs
TAG=solstice2002 DATE=1033430400000 node shoot.mjs
npx tsx photometry.mjs default2026             # 反解 ACES，比较环与行星盘
npx tsx photometry.mjs solstice2002
```

## 两处必须做对的地方

1. **I/F 的定义**：I/F = πL/E，所以朗伯面的 I/F = `albedo × mu0`，**不是** `albedo × mu0 / π`。
   环的反射率表用的也是这个约定（守恒厚层的法向入射反射率 ≈ 1.0，见
   `ring-multiple-scattering.test.js` 对 Chandrasekhar 公布值的校核）。
2. **行星盘的反照率**：必须按每个像素的经纬度去读它真正渲染的那张贴图，不能用整图均值——
   这个视角看到的是明亮的赤道带，逐像素实测 0.70，而整图均值只有 0.55。取贴图时还要注意
   three 的球面 UV 是 `u = atan2(z, -x)/2π`、且要用**网格本地**方向（先乘 attitude 的逆）。

第一版两处都错了，于是得出「环被压到物理值的 0.16、需要亮 5–6 倍」——**那个结论是错的**，
下面是用订正后的量测。采样还要剔除两类像素：被行星挡住的环面，以及盘内那些
「透过薄环看到的行星」（否则会把行星的亮度记到 C 环上，读出来 C 环比 B 环还亮）。

## 订正后的量测

屏幕值由 ACES + 曝光 1.12 反解回线性，`screen/I-F` 是该表面每单位 I/F 得到的场景辐射。

| 取景 | 行星盘 | B 环 | A 环 | C 环 | 环/行星（屏） | 环/行星（模型） | 环的实际份额 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 2026-09-15 默认（太阳仰角 −7.4°） | 1.17 | 0.832 | 0.769 | 0.895 | 0.119 | 0.167 | **0.71×** |
| 2002 至点默认（−26.7°） | 0.94 | 0.832 | 0.733 | 0.912 | 0.219 | 0.313 | **0.70×** |

两个取景给出同一个答案：**环被显示成物理值的约 0.70 倍，也就是比物理暗约 1.4 倍**
（不是 5–6 倍）。环内部的相对关系是对的：B/C 的对比在屏幕上 13×、模型 13.5×。

## 这 1.4 倍在哪一侧

- **环这一侧是对的**：屏幕/I-F = 0.83 ≈ 片元覆盖度（B 环 0.95）× 粒子色矢量的亮度（0.86）= 0.82，
  与代码逐行相符——环的着色器没有乘任何光强或 1/π。
- **行星盘那一侧偏亮**：three 把点光源的 `color × intensity` 当辐照度（`WebGLLights.js` 第 375 行），
  BRDF 再除以 π，所以行星盘每单位 I/F 本应得到 `2.6/π ≈ 0.83`，实测 0.94–1.17，多出约 1.4 倍。
  环境光（0.085）只能解释其中约 13%，其余来源未查明——这是**待查项，不是已解释项**。

## 试过又撤回的一步

按上面的推理把环的反射率乘上 `E/π`（E = 光源颜色 × 强度，随 `updateLighting` 每帧写入：
`uRingIrradiance`）本身是对的物理，但**实测让画面更偏离物理**：环的 screen/I-F 从 0.832 掉到 0.69，
环/行星的比值从 0.70 掉到 0.59。因为那 1.4 倍在行星盘一侧，单改环只会把两者的差距拉大。
这一步已撤回，留在本目录的只有量测与结论；要做的是先查明行星盘那 1.4 倍。

（动手时踩过一个坑：`THREE.Vector3.copy(THREE.Color)` 读的是 `.x/.y/.z`，颜色上只有 `.r/.g/.b`，
结果是三个 NaN 写进 uniform，环整条消失。要么 `.set(c.r, c.g, c.b)`，要么把 uniform 直接建成 `THREE.Color`。）

## 那 1.4 倍已排除的可能

| 假设 | 检验 | 结论 |
| --- | --- | --- |
| 采样的贴图不是应用渲染的那张 | 快照 `textureWidth` = 4096，正是 `8k_saturn.jpg`；换 `2k_saturn.jpg` 结果不变（1.167 vs 1.170） | 排除 |
| 贴图色彩空间处理不同 | `configure(texture, true)` 把基础贴图标为 sRGB，three 在采样时解码；按线性处理反而把偏差从 1.17 拉到 0.98 | 排除 |
| 光源强度语义与假设不同 | `WebGLLights.js:375` 把 `color × intensity` 直接当辐照度，`decay=0` 无距离衰减 | 排除 |
| 环境光 | 0.085 × albedo / π ≈ 场景辐射的 3%，按更宽松的算法也不到 13% | 只解释一小部分 |
| 高光项 | roughness 1 + F0 0.04，量级几个百分点 | 只解释一小部分 |
| 镜头补光 | `keyLight`/`fillLight` 仅在 `__promoOffline` 下可见 | 排除 |
| 我的反解只对灰色成立 | 对暖色（0.455, 0.386, 0.272）反解，与真实亮度差 5% 以内 | 排除 |
| 程序云/活动层 | `gasMap` 在 `flowAmount=1` 时最多给反照率加 ~0.04（约 6%） | 不足以解释 |

仍未查明：行星盘每单位 I/F 得到 0.94–1.17，而模型给 0.83（= 2.6/π）。**这是一个待查项，不是已解释项**，
在没有查清之前不应把差额写成常数塞进任何一处。
